# Тестовое задание: API платежей на FastAPI

## 1. Цель

Разработать небольшой сервис, через который онлайн-школа принимает оплату курса: API тарифов и платежей, включая получение списка платежей, и обработка уведомлений от банка.
Главное — точность денежных расчётов, обработка повторных запросов и корректные переходы статусов.

## 2. Стек

- Python 3.12+.
- FastAPI.
- Pydantic v2.
- PostgreSQL, Alembic и SQLAlchemy.
- pytest + httpx, testcontainers.
- Docker и Docker Compose.
- Ruff.
- GitHub Actions.

## 3. Предметная область и бизнес-правила

### 3.1. Тарифы

При старте создаются тарифы:

| Тариф    | Цена в рублях | Цена в копейках |
|----------|--------------:|----------------:|
| basic    |         9 900 |          990000 |
| standard |        19 900 |         1990000 |
| premium  |        29 900 |         2990000 |

### 3.2. Деньги

- Все суммы в API и базе данных хранятся в копейках, целым числом.
- Пример: 19 900 рублей → `1990000`.
- Использование `float/decimal` для денег запрещено.

### 3.3. Промокод

- `KVITTO10` даёт скидку 10% от цены тарифа.
- Регистр промокода не имеет значения.
- Неизвестный промокод — ошибка валидации с кодом `422`.

### 3.4. Способ оплаты

Допустимые значения `method`:

- `card`;
- `sbp`;
- `installment`.

Для рассрочки обязательно поле `installment_months` со значением `3`, `6` или `12`.

### 3.5. График рассрочки

- Сумма к оплате делится на срок рассрочки в копейках.
- Сумма всех платежей графика должна точно равняться сумме к оплате.
- Лишние копейки распределяются в первые платежи.
- Даты платежей не нужны.

Пример: тариф `standard`, без промокода, рассрочка на 3 месяца:

```python
amount = 1990000
schedule = [663334, 663333, 663333]
```

### 3.6. Статусы платежа

Новый платёж имеет статус `pending`.

Разрешённые переходы:

```text
pending -> succeeded
pending -> failed
succeeded -> refunded
```

Все остальные переходы запрещены.

## 4. API

### 4.1. GET /tariffs

- Ответ `200`: список тарифов.
- Поля каждого тарифа: `id`, `title`, `price`.

### 4.2. POST /payments

Поля тела запроса:

- `tariff_id`;
- `email`;
- `method`;
- `installment_months` — для рассрочки;
- `promo_code` — необязательно.

Поведение:

- `201` — платёж создан.
- Если передан заголовок `Idempotency-Key` и платёж с таким ключом уже существует, вернуть тот же платёж с кодом `200`,
  не создавая второй.

### 4.3. GET /payments/{id}

- `200` — платёж найден.
- `404` — платёж не найден.

### 4.4. POST /webhooks/bank

Банк сообщает о смене статуса платежа.

Запрос должен содержать заголовок `X-Signature` с HMAC-SHA256-подписью исходного тела запроса.

- Секрет задаётся переменной окружения `WEBHOOK_SECRET`.
- Подпись вычисляется по исходным байтам тела, без повторной сериализации JSON.
- Формат значения `X-Signature` в этом проекте: шестнадцатеричная строка HMAC-SHA256 без префикса.
- Проверка подписи выполняется до разбора тела и обработки уведомления.
- Отсутствующая или неверная подпись — `401`; состояние платежа не изменяется.

Поля тела запроса:

- `payment_id`;
- `status`.

Ответы:

- `404` — платёж не найден.
- `409` — запрещённый переход; статус платежа не изменяется. Тело ответа:

```json
{
  "error": "invalid_transition"
}
```

- `200` — успешное изменение статуса. Тело ответа:

```json
{
  "result": "ok"
}
```

### 4.5. GET /payments

- Ответ `200`: список платежей.
- Каждый элемент списка соответствует представлению платежа из раздела 4.6.
- Необязательные query-параметры:
  - `email` — фильтрация по точному совпадению email;
  - `status` — фильтрация по статусу платежа.
- Если переданы оба фильтра, применяются оба условия одновременно.
- Если фильтры не переданы, возвращаются все платежи.
- Если подходящих платежей нет, возвращается пустой список.
- Неизвестное значение `status` — стандартная ошибка валидации `422`.

### 4.6. Представление платежа

Платёж в ответах содержит поля:

- `id`;
- `status`;
- `tariff_id`;
- `amount`;
- `discount`;
- `method`;
- `installment_months`;
- `schedule` — список сумм в копейках или `null`;
- `email`;
- `created_at`.

### 4.7. Ошибки валидации

Ошибки валидации возвращаются в стандартном формате FastAPI с кодом `422`. Собственный формат не нужен.

## 5. Обязательные тесты

Обязательные сценарии для тестов на pytest:

1. Сумма с промокодом и без него, включая промокод в нижнем регистре.
2. График рассрочки: сумма графика равна сумме к оплате для сроков 3, 6 и 12 месяцев.
3. Повторный запрос с тем же `Idempotency-Key` не создаёт второй платёж.
4. Запрещённый переход статуса возвращает `409` и не изменяет статус платежа.
5. Запрос несуществующего платежа возвращает `404`.
6. Вебхук с корректной подписью выполняет разрешённый переход статуса.
7. Вебхук с отсутствующей или неверной подписью возвращает `401` и не изменяет статус.
8. Изменение тела запроса после вычисления подписи приводит к `401`.
9. Список платежей корректно фильтруется по `email`, по `status` и по обоим параметрам одновременно.
10. При отсутствии подходящих платежей список платежей возвращает `200` и пустой список.
11. Неизвестное значение фильтра `status` возвращает `422`.

Для тестов бизнес-правил вебхука, включая ответы `404` и `409`, запрос должен иметь корректную подпись.

Тесты должны проверять результат, а не только код ответа.

## 6. Запуск и конфигурация

- Приложение и все зависимости запускаются командой `docker compose up`.
- Запуск на пустой базе включает применение миграций перед запуском API.
- Порядок запуска учитывает готовность базы данных к подключениям.
- Конфигурация подключения к БД и секрет вебхука передаются через переменные окружения.
- В репозитории находится `.env.example` с примером необходимых переменных без реальных секретов.
- Реальные секреты и локальный `.env` не добавляются в Git.

## 7. Автоматические проверки

- В GitHub Actions настроен workflow, запускаемый на каждый `push`.
- Workflow выполняет `ruff check .` и `pytest`.
- Для тестов предоставляется отдельная PostgreSQL-база (Testcontainers) и необходимые переменные окружения.
